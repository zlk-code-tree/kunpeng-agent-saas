# 备份与恢复

## 备份范围

项目备份脚本覆盖：

- PostgreSQL 业务数据库。
- 对象存储 Volume。
- SHA-256 完整性校验清单。

Redis 队列不包含在备份脚本中。恢复后，已提交到数据库 Outbox 的待派发任务可以重新派发；运行中的任务需要根据实际状态复核。

## 执行备份

备份目录必须使用绝对路径：

```bash
BACKUP_DIR=/data/backups/gin-dify-saas make backup
```

脚本会创建带 UTC 时间戳的目录：

```text
/data/backups/gin-dify-saas/gin-dify-saas-YYYYMMDDTHHMMSSZ/
├── postgres.dump
├── objectstore.tar.gz
└── SHA256SUMS
```

数据库使用 PostgreSQL custom format，可由 `pg_restore` 恢复。对象存储卷保存为 gzip tar 包。

## 校验备份

进入备份目录执行：

```bash
shasum -a 256 -c SHA256SUMS
```

两个文件都应显示 `OK`。应定期在隔离环境验证恢复，而不是只确认备份脚本退出成功。

## 恢复前检查

恢复是覆盖性操作：

- PostgreSQL 使用 `--clean --if-exists` 恢复对象。
- 对象存储卷会先清空，再解压备份。

恢复前必须确认：

1. 目标环境和备份来源正确。
2. API 和 Worker 已停止，避免恢复期间继续写入。
3. 已为目标环境当前状态创建额外备份。
4. 备份校验通过。
5. 数据库版本与应用版本兼容。

## 执行恢复

先停止应用写入，但保留基础设施：

```bash
docker compose \
  --env-file deploy/.env.prod \
  -f deploy/compose.yaml \
  -f deploy/compose.prod.yaml \
  stop api worker web
```

设置固定确认变量并执行：

```bash
CONFIRM_RESTORE=gin-dify-saas \
  ./deploy/scripts/restore.sh \
  /data/backups/gin-dify-saas/gin-dify-saas-YYYYMMDDTHHMMSSZ
```

恢复完成后启动应用：

```bash
docker compose \
  --env-file deploy/.env.prod \
  -f deploy/compose.yaml \
  -f deploy/compose.prod.yaml \
  up -d api worker web
```

## 恢复后验收

至少检查：

- API `/readyz` 返回成功。
- 管理员能够登录。
- 租户、智能体、知识库记录存在。
- 随机抽查对象存储文件可读取。
- Worker 没有持续解密失败或数据库版本错误。
- Dify 和模型供应商凭据可以正常解密。

数据库恢复时必须使用与备份时匹配的 `CREDENTIAL_ENCRYPTION_KEY`，否则外部集成密文无法解密。
