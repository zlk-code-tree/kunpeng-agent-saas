# Gin Dify SaaS 项目部署架构

## 文档用途

本文描述当前仓库实际包含的部署组件、容器职责和数据流。回答“现在部署了什么”“完整项目包含什么”“Dify 是否必须部署在客户侧”等问题时，以本文为基础。

## 当前项目的完整组件

完整的 Gin Dify SaaS 平台由以下组件组成：

| 组件 | Compose 服务 | 作用 | 是否保存业务数据 |
|---|---|---|---|
| Vben Admin 前端 | `web` | 提供浏览器管理界面，通过 Nginx 代理 `/api/` | 否 |
| Gin API | `api` | 登录、租户、智能体、知识库、计费和管理接口 | 否 |
| Gin Worker | `worker` | 消费 Asynq 任务、调用 Dify、处理 Outbox 和运行结算 | 否 |
| PostgreSQL | `postgres` | 保存用户、租户、智能体配置、运行记录和计费数据 | 是 |
| Redis | `redis` | Asynq 队列和运行时基础设施 | 是，开启 AOF |
| SeaweedFS S3 | `objectstore` | 保存知识库上传文件和导出文件 | 是 |
| Dify | 外部独立服务 | 执行 Chatbot、Agent、Chatflow、Workflow 和知识库索引 | 取决于部署模式 |

`deploy/compose.yaml` 只定义 PostgreSQL、Redis 和对象存储，因此 Docker Desktop 中只看到这三个容器时，表示“基础设施已启动”，不表示整个项目已经部署。

`deploy/compose.prod.yaml` 增加 `api`、`worker` 和 `web`。生产部署时必须同时叠加两个 Compose 文件。

## 两种 Dify 部署方式

### 平台托管 Dify

客户侧部署：

```text
Web + API + Worker + PostgreSQL + Redis + 对象存储
                         |
                         +---- HTTPS ----> 平台托管 Dify
```

客户侧不需要安装 Dify，但必须允许 API 和 Worker 访问托管 Dify 地址。提交给 Dify 的问题、文档内容、检索上下文和输出可能离开客户网络，因此这是混合部署。

### 客户私有 Dify

客户侧同时部署 Dify、向量数据库和模型服务，适用于合同、简历、报价等敏感数据场景。Gin SaaS 平台通过 Dify 实例配置连接客户本地 Dify。

## 请求链路

```text
浏览器
  -> web/Nginx
  -> Gin API
  -> PostgreSQL 保存运行与 Outbox
  -> Redis/Asynq
  -> Gin Worker
  -> Dify
  -> 模型和知识库
```

API 和 Worker 使用同一份业务配置。API 负责接收请求和写入任务，Worker 负责耗时的模型调用。即使是单用户部署，也不应省略 Worker。

## 持久化边界

- PostgreSQL 数据位于 Compose Volume `deploy_postgres_data`。
- Redis 数据位于 `deploy_redis_data`，Redis 使用 AOF。
- 对象文件位于 `deploy_objectstore_data`。
- 执行 `docker compose down` 默认不会删除这些卷。
- 执行 `docker compose down -v` 会删除卷，不应作为常规重启命令。

## 端口

开发基础设施默认映射：

| 服务 | 宿主机端口 | 容器端口 |
|---|---:|---:|
| PostgreSQL | 15432 | 5432 |
| Redis | 16379 | 6379 |
| SeaweedFS S3 | 18333 | 8333 |

生产 Web 默认映射宿主机端口 80，可通过 `WEB_PORT` 修改。API 的 8080 端口只在 Compose 网络内使用，由 Web 容器代理。
